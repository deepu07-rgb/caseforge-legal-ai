# End-to-end run through the real app — 2026-10-11

The Stage 4 gates test engines one at a time. This run drove the **actual desktop app** (`tauri dev`, WebView2) through its screens on a throwaway vault, to find what the gates cannot.

**Method.** The app was built from `main` (`3997faf`) with a separate app identifier so its data could not touch any real vault, started with WebView2's remote-debugging port, and driven over the Chrome DevTools Protocol: real clicks, real file input, real text entry, real `invoke` calls to the host, real Tesseract, real Ollama (`qwen2.5:7b`). Nothing was mocked. The throwaway vault, the build output and the clone were deleted afterwards.

## What was driven, and worked

Create the vault password → create a case in the wizard (India, Criminal, Defence) → upload five Hindi scans (FIR, order, statement, degraded FIR, mixed Hindi/English) by the file input → triage → recognize each → Hindi to English tab, *Translate* over all documents → confirm a case-number field → *Show facts read from this translation* → Review understanding, select an item. Then every one of the 18 left-hand screens was opened in turn.

* Recognition routed Hindi pages to `hin+eng` and the English page to the English reader; page scripts came out Hindi / Hindi and English / English; the review panel shows "· HINDI" beside the page.
* Translation: 35 segments in about 90 seconds, original beside English, every segment labelled, every critical field "not confirmed". Confirming a field showed "confirmed by you as …", with Withdraw beside it. The facts panel listed the order's two dated events as "from a translation — not confirmed".
* 18 of 18 screens rendered with **no console error and no exception**.

## Defects found and fixed in this commit

1. **The packaged app did not ship the confidence calibration maps.** `eval/calibration/` was not in the Tauri bundle resources. In the app's own layout the English recogniser failed outright ("local OCR exited unexpectedly"), and every Hindi word came back uncalibrated, so every word was marked low-confidence and every field held. This has been so since the English calibration (B-S3-05); no gate saw it because they run from the source tree and the installed-layout smoke test never checked for the files. Fixed: `eval/calibration/**/*` is bundled, the smoke test checks the four files, and the Hindi gate asserts both. Verified in the app: a fresh recognition run now calibrates every word (Hindi pages: 1-3 low-confidence words of 50-85, 0-2 fields held; the English page: 0 of 44).
2. **A held item was shown GREEN.** The provenance badge in Review turned any item with a source pointer GREEN "MATTER EVIDENCE", including a date OCR had misread and the engine had held. A pointer is not a verification. A held or machine-translated item now shows AMBER with the reason.
3. **Stale copy**: the text-layer panel said "Offline English OCR" and named a "provisional" recogniser; both now name the English and Hindi recognisers.
4. The facts panel promised "until you confirm them" but offers no way to confirm a fact; it now says to check each against the original.

## Seen but not fixed

* The **language** column says "en" for Hindi documents: the upload tags every file English. It does not affect reading (the script is detected from the page), but it is wrong on screen.
* **Triage** gives Hindi pages the frozen class "typed_english" at low confidence; the frozen class set has no Hindi class, so the script label (Hindi) is what the screens use.
* The deterministic matter-graph builder cannot read Devanagari, so a Hindi matter has an almost empty case graph until its facts are read from the translation, which stays a separate unconfirmed graph. Confirming a translated fact into the matter is not built.

## Not exercised

Skeleton extraction and everything downstream of it on these pages (Digest, Mock Court, Argument Analysis are blocked until a graph and a confirmed legal regime exist), Deadlines and Code Bridge data entry, the Opponent's Filing and Witnesses flows, Chambers screens, Encrypted Bundle Exchange, editions and licences, voice. Those still have only their engine tests.

# Second run — English matters, witnesses, opponent's filing, deadlines

Same method (the real app, a throwaway vault, nothing mocked), on two English matters built from the pinned goldens: the 40-page synthetic chronology (`G-CASE-IN/synth_chrono_40`) and the impeachment case (`G-IMPEACH`: FIR, s.161 statements, examinations-in-chief), plus the opposing reply (`G-OPPOSING`).

## Defects found and fixed

1. **A digital document with a date in it never reached the case graph.** Every native-text page (a digital PDF, a text file) that contained a date, an amount or a section number was marked "warned" and left out of case-graph extraction, because native text has no engine confidence and "missing" confidence forces review of every field on it. Result in the real app: from 4 documents holding 20 dated events, **0 events** (and no statutes, no evidence) — the Digest chronology was empty. Present since B-S3-05; the chronology gate calls the extractor directly and never goes through the page layer, so it passed. Fixed: a native page is warned only when it has no text; a field in exact text is held only when its own check fails (an impossible or ambiguous date, a malformed amount). Word confidence stays "missing", honestly, so the frozen `page_text_layer` schema is untouched. In the app: **20 of 20** known dates, plus 1 statute (Section 138) and 2 parties; the journey now reads "20 events · 2 parties · ready". The confidence gate carries the regression (a well-formed field in native text is not held; an impossible date still is; a native page warns only when empty).
2. **The Witnesses register was unusable at the app's default window (1024 px):** the document name wrapped a letter per line and the witness, kind and date columns were squeezed to a sliver. The table now scrolls sideways inside its card and its columns keep a readable width.

# Follow-up: the expired-licence read-only guard (finding 1 of the third run)

Decision taken with the owner: an expired licence keeps reading, listing and exporting open and refuses every other change to a matter, enforced in one place.

* **How:** when the licence status says the vault is not writable, every open matter database is put into SQLite's query-only mode (`VaultManager::apply_write_policy`). It is applied whenever the licence status is read (the Licence screen, activation, the expiry test button) and whenever a matter is opened, and lifted as soon as a valid licence makes the vault writable. SQLite's own refusal is shown as the product's `CF_VAULT_READ_ONLY` message. No command has to remember a guard.
* **Proved** by a vault test: with a writable vault a document upload, a case-graph write, a translation write and a witness-store write all succeed; after an expired licence is activated each is refused with `CF_VAULT_READ_ONLY`, the refused upload leaves nothing behind, the same reads still work, closing and reopening the matter does not lift it, and activating a valid licence does, without reopening. The editions gate (AC-S3-22.8) now requires that test and the single choke point in the source.
* **Not covered, deliberately:** the app-level stores (licence, air-gap, contacts, installed packs) stay writable so a licence can be renewed and packs installed; installing newer official packs is separately refused when the pack subscription has ended.
* **Not re-run in the desktop app:** the vault test exercises the real vault code; the screen-level re-test (upload after *Mark expired*) was not repeated.

# Follow-up: relief, exhibits and the authority list (findings 3 and 4 of the third run)

* **Relief and evidence.** The extractor read relief only from a one-line `Prayer: ...` and evidence only from a one-line `Exhibit: ...`, which is not how a pleading is written. It now also reads a `PRAYER` / `RELIEF SOUGHT` / `WHEREFORE` heading with its numbered or plain paragraphs below it, a sentence `... prays that / for / to ...`, and an exhibit or annexure cited in running text (`Exhibit P-3`, `Annexure A-2`, once each, with the line it appears in). Each item points at its own words in the page. The same relief written as a heading block and as a `prays that` sentence is one relief, not two; the phrase "prayer meeting" is not relief; "the exhibit that was filed" is not an exhibit. Tests: four in `docpipe::skeleton`, including one on the pinned chronology page (`prays for interim protection and recovery of INR 1,25,000`, `Exhibit A-1`). The 20-of-20 chronology is unchanged.
* **Authority suggestions.** For a matter that is plainly civil (its type, title or court say civil, partition, property, contract, suit, decree ... and nothing says criminal, bail, sessions, accused ...) the suggestions no longer include the criminal codes (BNS, BNSS, IPC, CrPC), unless the matter's own papers cite one. They are not hidden: the screen lists what was left out and why, and says to search for them if needed; nothing about counsel's own decisions changes. Evidence law is never filtered. Tests: three in `working_set`.
* **Not re-run in the desktop app.** Both are covered by Rust tests on the real extractor and the real suggestion rule, and the screen change type-checks; the click-through on a memo was not repeated. The sentence rule ends a relief at a full stop, so an abbreviation such as "Rs." inside a `prays that` sentence cuts it short.
